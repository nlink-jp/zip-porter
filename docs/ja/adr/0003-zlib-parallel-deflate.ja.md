# ADR-0003: zlib による単一ファイル並列 deflate

| 項目 | 内容 |
|------|------|
| Status | **Accepted** |
| Date | 2026-08-01 |
| Decision makers | nlink-jp maintainers |
| Triggered by | ADR-0002 でエントリ単位の並列化は入ったが、単一の大きなファイル — LLM のモデルアーカイブ、ディスクイメージ — は依然として 1 コアで圧縮される |

> もとは `nlink-jp/.github` の組織 ADR-014 として記録していた。
> 2026-08-03 にここへ移設。組織の ADR ログは組織全体を拘束する決定のための
> ものであり、この決定が拘束するのは 1 つのアプリだけである。

## Context

ADR-0002 はエントリを**またいで**並列化した。1 エントリの**内側**では、Apple の
Compression framework は並列化できない。エンコーダの finalize がすべての
ストリームを BFINAL ブロックで終えるため、独立に圧縮したセグメントを 1 本の
妥当な deflate ストリームに連結できないからである。ユーザーが挙げた用途 —
LLM のモデルファイルとディスクイメージのパック — はまさに「巨大な単一ファイル」
という形で、ADR-0002 からは何も得られない（圧縮不能なモデル重みはプローブに
よってすでに `store` へ迂回する。問題は**圧縮可能な**大きいファイルで、これが
1 コア分の速度で走る）。

macOS は zlib を同梱しており（1.2.12。SDK に `zlib.h` と `libz.tbd` がある）、
リンクしても同梱依存は増えない。180 MB のテキストファイル、12 コアでの実測:

| 経路 | 実時間 | 出力 |
|------|--------|------|
| Compression framework、1 コア（出荷中） | 2.82 s | 26.0 MB |
| zlib level 6、1 スレッド | 4.23 s | 22.5 MB |
| **zlib level 6、12 スレッド** | **0.44 s** | **22.5 MB** |
| zlib level 1、12 スレッド | 0.10 s | 33.3 MB |
| zlib level 9、1 スレッド | 21.25 s | 20.6 MB |

形を決めるのは 3 つの事実である。並列スケーリングがほぼ線形であること
（12 スレッドで 9.4 倍 — メモリ律速ではない）、約 16 MB のブロックに分割しても
圧縮率の劣化が計測できないこと、そして level 9 は level 6 の 5 倍遅くて
約 1 % しか縮まない（提供する価値がない）こと。zlib level 6 は
`ditto`/Info-ZIP と出力サイズも一致するので、v0.1.0 以来抱えてきた
1.5〜10 % のサイズペナルティも解消する。

連結の手法は pigz のものである。各ブロックを raw deflate として圧縮し
`Z_SYNC_FLUSH` で終え（バイト境界に揃い、BFINAL が立たない）、順に連結して、
最後のブロックだけ `Z_FINISH` で終える。結果は 1 本の標準的な deflate
ストリームで、非標準なものはリーダーに一切届かない。ブロックごとの CRC は
`crc32_combine` で合成する。pigz はさらに各ブロックを直前のブロックの末尾
32 KB で辞書プライムするが、実測ではここでの利得はノイズ以下だったので、
その結合は行わずブロックを完全に独立に保つ。

## Decision

**deflate を zlib の level 6 に切り替え、大きいエントリは独立ブロックとして
並列に圧縮する。** inflate は Compression framework のままにする。展開は
そもそもボトルネックではなく、入力も標準的な deflate ストリームのままで
変わらない。

1. **`ZipPorterCore` に `CZlib` システムライブラリターゲットを追加。**
   SDK の zlib のみ。ソースの vendoring も、同梱依存の追加もしない。
2. **deflate はすべて zlib を通す** — エントリ並列の経路も、ブロック並列の
   経路も、ライタの逐次フォールバックも。1 つのエンコーダがすべてのアーカイブを
   生成し、出力は決定的なままになる。
3. **サイズ閾値を超えるエントリは約 16 MB のブロックとして波状に並列圧縮する**
   （同時に `cores` ブロック: 読み込み、並行圧縮、順に追記、ADR-0002 と同じ
   スピル）。ピークメモリはファイルサイズに依らず `cores × 2 × blockSize` 程度に
   留まる。ブロックごとの CRC は `crc32_combine` で合成する。
4. **ユーザー向けの圧縮レベルは設けない。** level 6 は現在の出荷物より速く
   **かつ**小さく、level 9 は 5 倍の時間で約 1 %、level 1 は波状パイプラインが
   すでに出している速度と引き換えに 11 % 大きい出力になる。ノブを付けることは
   「より悪い点を選ぶ 3 通りの方法」を提供することでしかない。実際のワーク
   ロードが別の結論を示したときにだけ再検討する。

圧縮不能プローブ（ADR-0002）は引き続き先に走る。モデル重みなど、すでに圧縮
済みの巨大ファイルは I/O 速度で `store` へ迂回し、deflate 経路に到達しない。

## Consequences

**Positive**

- 圧縮可能な単一の大きいファイルは、13 % 小さい出力でおよそ 6 倍の実時間短縮を
  得る。すべてのアーカイブが `ditto` 並みのサイズに縮む。
- リーダーが見る deflate ストリームは完全に標準のままで、既存の相互検証スイート
  （Info-ZIP、ditto、7-Zip、フィクスチャ経由の Windows Explorer）が引き続き
  ゲートになる。

**Negative / accepted trade-offs**

- ストリームのフレーミングを手組みする（sync flush での連結、最後だけ final
  ブロック）というフォーマットレベルのコードを自前で抱えることになる。
  ラウンドトリップ・外部ツール・決定性の各テストが安全網である。
- 同じ入力に対するアーカイブのバイト列が v0.5.0 のものと変わる（エンコーダが
  違う）。決定性はバージョン内で保証するもので、バージョンをまたいだ安定性は
  約束していない。
- 小さいエントリは Compression framework に対して zlib の単一ストリーム約 2 倍の
  コストを払うが、これはエントリ単位の並列化が吸収する。コーパスのベンチマークが
  退行を監視する。
