# ADR-0006: Deflate64 展開を自前デコーダで実装する

| 項目 | 値 |
|------|-----|
| 状態 | **承認** |
| 日付 | 2026-10-31 |
| 決定者 | nlink-jp メンテナ |
| きっかけ | Windows Server 2012 のエクスプローラ（「送る → 圧縮 (zip 形式) フォルダー」）で作った 2.8 GB の ZIP が ZipPorter では展開に失敗し、`unzip` では展開できた |

## 背景

Windows エクスプローラ標準の ZIP 作成は、まとめるファイルがおよそ 2 GB を
超えると圧縮方式を Deflate（方式 8）から **Deflate64**（方式 9、
"enhanced deflate"）に切り替える。Microsoft はこの閾値を文書化していないが、
利用者や、同じ理由で Deflate64 対応を追加したツールの報告で一貫している。
v0.12.0 までの ZipPorter は store（0）と Deflate（8）しか展開できず、
大きなエクスプローラ製 ZIP はすべて `unsupportedMethod(9)` で失敗していた。
GUI にはこの列挙値がそのまま、翻訳されずに表示されていた。Info-ZIP `unzip`
（macOS 版は `USE_DEFLATE64` 付きでビルド）と 7-Zip は読めるため、
「ターミナルでは展開できる」ことになる。ZipPorter は Windows から ZIP を
受け取るためのアプリであり、Windows が作った ZIP を開けないのは明確に
スコープ内の欠陥である。

Deflate64 は Deflate に対する次の変更だけでできている。

1. 窓が 32 KiB ではなく 64 KiB。距離符号 30・31（Deflate では未使用）が
   32769・49153 ＋拡張 14 ビットを表す。
2. 長さ符号 285 が固定長 258 ではなく、3 ＋**拡張 16 ビット**
   （最大 65538）を表す。
3. それ以外（ブロック種別、ハフマン符号の構成、符号長の符号化）は
   Deflate と同じ。

macOS に同梱のデコーダはない。Compression フレームワークは生の Deflate
のみで、システムの zlib は `infback9`（contrib モジュールで、ライブラリ
本体には含まれない）を公開していない。組織の方針としてコミュニティ製
ライブラリは採用しない（サプライチェーン方針）。残るのは自前実装である。

## 決定

**方式 9 は ZipPorterCore 内の自前・純 Swift のストリーミングデコーダ
（`Inflate64`）で展開する。Deflate64 の作成は行わない。**

1. **デコーダは 1 つ、変種は 2 つ。** `Inflate64` は RFC 1951 を実装し、
   `variant`（`.deflate` / `.deflate64`）で上記 2 つの表と窓サイズだけを
   切り替える。本番で使うのは方式 9 のみで、方式 8 は従来どおり
   Compression フレームワーク（ADR-0003）。`.deflate` 変種は、少数の
   Deflate64 フィクスチャだけでなく、システム zlib が大量に作れる
   ストリームでデコーダを試験するために置く。
2. **入力は引き出し、出力は押し出し。** デコーダはペイロードのチャンクを
   クロージャから引き出し、出力は他の方式と同じ `out` シンクへ流す。
   これによりエントリごとのサイズ上限（fail-fast）、CRC 検査、
   ZipCrypto/AES 復号、AES トレーラ処理を作り直さず共有する。最終
   ブロックの後は、残ったペイロードを読み切って AES の HMAC が全バイトを
   見るようにする。
3. **zlib と同等に厳格。** 過剰割り当て・不完全なハフマン符号は拒否する
   （RFC 1951 が許す 1 ビット符号 1 個の場合を除く）。出力の先頭より前を
   指す距離、無効なシンボル、`NLEN` が `~LEN` でない格納ブロック、符号数を
   超える繰り返し符号、ブロック終端を持たないリテラル/長さ符号、最終
   ブロック前に尽きる入力も拒否する。失敗はすべて既存の「構造が不正な
   ため拒否」メッセージ（`corrupt(…)`）として出し、トラップにはしない。
4. **メモリは有界。** 64 KiB の履歴と固定長のステージングバッファのみで、
   エントリサイズに依存しない。デコードの各ステップは入力を消費するか
   出力を出すので、アーカイブが空回りさせられるループはない。
5. **作成はしない。** Deflate64 で作っても得るものがなく（zlib の出力は
   どこでも読める）、相手が開けない ZIP を作ることになる。
6. **未対応の方式には文章で答える。** まだ読めない方式（bzip2、LZMA など）
   は、生の列挙値ではなく方式番号を含む翻訳済みメッセージで知らせる。

## 結果

**良い点**

- Windows エクスプローラ製の大きな ZIP が、アプリでも Finder からでも
  CLI でも展開できる。このアプリが作られた目的そのものの場面である。
- デコーダは 3 方向から照合する。遠い距離の符号を必ず使わせるデータで
  作った 7-Zip の Deflate64 フィクスチャ（使われたことはデコーダの
  カウンタで確かめ、仮定しない）、`.deflate` 変種に通す zlib 製の
  Deflate ストリーム、そして手組みのストリーム。手組みは、7-Zip の
  エンコーダが一度も出さないと実測した拡張 16 ビットの長さと、
  拒否規則ごとの不正入力に使う。

**悪い点・受け入れる残余**

- 純 Swift のデコーダは Compression フレームワークより遅い。動くのは
  方式 9、つまり作成側がそれを選んだアーカイブだけである。実測の
  スループットは、これを出すリリースの CHANGELOG に記録する。
- 攻撃者が与えるデータを読むパーサが 1 つ増える。ADR-0001 の規律に
  従う：出力上限と CRC は引き続き効き、上記の厳格さにより、完全に
  デコードされずに受け入れられる入力は残らない。
- エクスプローラの閾値は利用者報告に基づく。実装はこの値に依存しない。
  方式 9 は現れればどこでもデコードする。
