# ADR-0005: 所有権を記録する後始末・ローカルヘッダ由来のエントリ範囲・圧縮メモリの総量予算

| 項目 | 内容 |
|------|------|
| Status | **Accepted** |
| Date | 2026-09-05 |
| Binds | zip-porter |
| Decision makers | nlink-jp maintainers |
| Triggered by | v0.11.2 に対する外部コードレビュー（2026-09-05）: 指摘 4 件、うち 3 件は CLI と Core で再現、1 件は計測 |

## Context

リリース済みコードの独立レビューが 4 件の欠陥を報告した。いずれもレビュワーが
再現または計測しており、変更に着手する前にソースに照らして再検証した:

| ID | 観測 | 箇所 |
|----|------|------|
| ZP-01 | 失敗した展開が、自分が作っていないファイルを削除する。`topItems` は*作成予定*のトップレベルパスの一覧で、何も存在しない時点で埋められ、失敗経路はその全項目を削除する。名前確認と `O_EXCL` 作成の隙間に現れたファイルは作成を失敗させ、catch ブロックがそのファイルを消す。予定名にあるリンク切れシンボリックリンクも同じ運命になる。`.never` ポリシーでは、寛容な `createDirectory` が他者の作ったばかりのフォルダの*中へ*展開までする。 | `Unpacker.unpack` |
| ZP-02 | 重複検査（ADR-0001 §3）は各エントリの範囲を `localHeaderOffset + 30 + <中央ディレクトリの名前長> + compressedSize` と計算するが、展開は `localHeaderOffset + 30 + <ローカルの名前長> + <ローカルの extra 長>` から読み始める。互いの extra フィールドにローカルヘッダを入れ子にした 2 エントリは検査を通り、同じ 1 バイトを読む。 | `ZipReader.validateEntryRanges` と `ZipReader.extract` |
| ZP-03 | 退避出力用の一時ファイルは、最初のバッファを書き終えるまで記憶されない。途中で失敗した書き込みは誰も知らないファイルを残す。別に、`compressLarge` は失敗分岐のうち 2 つで `abandon()` を呼び、他（読み取り・emit・クローズ）では呼ばない。 | `ParallelCompressor.SpillSink`、`compressLarge`、`compressOne` |
| ZP-04 | 16 MiB の退避しきい値は、圧縮中の 1 エントリの出力を有界にする。しきい値未満の完了結果は全エントリが終わるまでメモリに残るため、保持総量は入力に比例して増える — 1 MB 入力 64 件で 50 MB を保持 — が、ADR-0002 は上限を `concurrency × threshold` と述べている。 | `ParallelCompressor.compress`、`Packer` |

レビュー指摘の組織規則（CONVENTIONS §*Root cause before patch*）は、直す前に
分類することである。4 件は 3 つのクラスに落ち、最初のクラスには 3 つの事例がある:

- **クラス A — 所有権を計画から推定し、作成時に記録していない。** ZP-01
  （予定の `topItems` を失敗時に削除）、ZP-03a（`spillURL` を最初の書き込みの後に
  代入）、ZP-03b（列挙した一部の出口でだけ解放を呼ぶ）。いずれもコードは何を
  *作るつもりだったか*を知っていて、その意図で後始末する。作成システムコールが
  実際に成功したか、どのパスに対してかは、後始末が参照するものになっていない。
- **クラス B — 1 つの事実を 2 つのソースから 2 回導出している。** ZP-02: データ
  範囲を検査では中央ディレクトリから、読み取りではローカルヘッダから計算する。
  検査の強さは、フォーマットが一致を要求していない 2 つの導出の一致度を超えられない。
- **クラス C — 単位ごとに掛けた上限を総量の主張にしている。** ZP-04: しきい値は
  各シンクに強制されるが、シンクが返すものの合計には何も強制していない。

レビューの 5 つ目の観測は製品の欠陥ではない: UTF-8 ロケールでは `unzip -t` が
日本語名の一部バイトを多バイト列の*内側*で `?` に置換するため、出力は妥当な
UTF-8 ではなく、テスト補助関数の厳密デコードが空文字を返す。当方でも再現し、
`LC_ALL=C` ではテストは通る。

**独立設計検証。** 本記録の初稿は CONVENTIONS が要求する設計検証パス（新鮮な
コンテキストのレビュワーがナレッジベースとワークスペースの教訓と突合する）を
通した。所見のうち 4 件が設計を変え、以下で *検証後* と印を付ける: トップレベル
フォルダの claim を最初の書き込みの前へ移動、一意性確認を `lstat` 意味論へ、
エントリごとの一時ファイルを pack ごとの 1 つの arena へ置換、圧縮器のノブを
プロセス全域の static から呼び出しごとの引数へ。2 件は受容残余として記録し、
1 件（2 プロセス競合の E2E）は非決定的として不採用 — 進捗コールバックへの介入が
同じシステムコール結果を決定的に再現する。

## Decision

**各クラスを `ZipPorterCore` の構造で閉じ、クラスを名指しするテストで固定する —
事例ごとの振る舞いテストと、エンジンのソースを読んで第 2 の削除点・第 2 の導出・
第 2 の一時ファイル寿命で失敗する `ArchitectureTests`。レビュワーの再現手順は
回帰テストとして採用する。レビュワーの修正案はそのままは採用しない（*Alternatives*
参照）。**

### A. 所有権は作成システムコールの時点で記録し、1 箇所から解放する

**展開。** トップレベル項目 — ラッパーフォルダ、または `.never` の場合は各
トップレベルのファイルとディレクトリ — は*排他的に*作成する。ファイルは従来どおり
`open(O_CREAT|O_EXCL)`、ディレクトリは `mkdir(2)`（`PathUtil.createDirectoryExclusively`）
で、パスに何かあれば（リンク切れシンボリックリンクを含め）`EEXIST` で失敗する。
URL は、その呼び出しが成功を返した後にだけ `OwnedItems` 台帳へ追加する。失敗経路は
`owned.removeAll()` を呼び、予定名にはアクセスできない。書き込み失敗後のエントリ
ごとの `removeItem` は撤去し、台帳が展開器の唯一の削除者になる。したがって一意性
確認と作成の間に他者が取った名前は、この展開にとって*エラー*（`File exists`）であり、
他者のディレクトリを再利用することも、他者のファイルを削除することも決してない。

*検証後:* トップレベルの**フォルダ**はすべて、最初のエントリを書く前に、展開と
同じ `do/catch` の中で claim する。初回使用時の遅延 claim は、確認から作成までの窓を
展開の全時間 — `.never` で多数のフォルダなら数分 — 開いたままにしていた。トップ
レベルの**ファイル**は到達時に自身の `O_EXCL` 作成で claim する。ファイルは書かずに
claim できず、そこでの衝突も安全に失敗する。*検証後:* 一意性確認（`PathUtil.uniqueName`、
`PathUtil.uniqueURL`）は「存在する」を `lstat` 意味論（`PathUtil.somethingExists`）で
答える。`fileExists(atPath:)` はシンボリックリンクを追い、リンク切れを「無い」と
報告するため、確認が選んだ名前で排他作成が — 競合ではなく決定的に — 失敗していた。
エントリは「name 2」に着地し、リンクには触れない。

**圧縮の一時領域。** *検証後*、初稿の「エントリごとの一時ファイル + defer による解放」
を置き換えて、`compress` 呼び出しごとに 1 つの `ScratchArena`。最初の退避時に —
排他的に、アーカイブの隣の隠しランダム名（`.zp-scratch-<uuid>`）で — 作成し、ハンドル
は同じロックの中の同じ手順で記録するので、ファイルが所有者なしに存在する瞬間はない。
ワーカーはロック下で追記してバイト範囲を受け取り、結果の保持先は `.memory(Data)` か
`.arena(ScratchArena, [Range<UInt64>])` で、ライタはその範囲を読み戻す。arena の所有者は
1 つ: `compress` はどの失敗でもそれを削除し、返す `Output` は `Packer` に渡して、その
単一の `defer` が `cleanUp()` を呼ぶ。あらゆる出口で正しく扱うべきエントリごとの寿命は
残っておらず — ZP-03 の形は再発し得ない — メモリ予算（C）がユーザーのフォルダに
数千の一時ファイルを散らかすこともない。

*検証後:* 圧縮器のノブ — 退避しきい値、メモリ予算、一時ファイルのオープナ — は
`ParallelCompressor.Limits` に載せて呼び出しごとに渡す（`Packer` に内部の
`pack(limits:)` オーバーロードを追加）。テストが書き換えて復元するプロセス全域の
static ではない。オープナを注入可能にするのは、実際のファイルシステムは書き込みを
合図で失敗させてくれないからである。

### B. エントリ範囲はオープン時にローカルヘッダから 1 回だけ解決する

`ZipReader.resolveEntryRanges` はアーカイブを開く際に各ファイルエントリの 30 バイトの
ローカルヘッダを読み、`dataOffset = localHeaderOffset + 30 + localNameLength +
localExtraLength` を計算して `ZipEntry` に保持し、重複検査と EOF 検査を
`[localHeaderOffset, dataOffset + compressedSize)` に対して行う。`extract` は
`entry.dataOffset` から始め、ヘッダを読まない。導出は 1 つで、両方の消費者がそれを
使う。すべての境界は既知の正しいファイルサイズからの減算（`headerLength <= fileSize -
start`、`compressedSize <= fileSize - dataOffset`）で表し、検査の中でヘッダ値を加算
しない — v0.10.0 のクラッシュから得た AGENTS の規則。extra フィールドや名前長が
ペイロードを EOF の先へ押し出す場合は、展開中ではなくオープン時に拒否する。

*検証後:* エントリはオフセット順に訪れ、ヘッダは 256 KiB の窓から供給する。10 万件の
小さなエントリは 1 件 1 回ではなく数百回の読み取りで済み、ネットワークボリューム上で
一瞬か数分かの差になる。大きなエントリはヘッダ 1 件 1 回に戻るが、そのとき件数は少ない。
計測: 10 万エントリのアーカイブ（10.8 MB）のオープンと一覧はローカルで 0.4 秒。

### C. 保持する圧縮出力に総量予算を設ける

1 回の `compress` 呼び出しで共有する `MemoryLedger` が、メモリに残る各完了結果の
バイト数を予約する。保持総量を `cores × spillThreshold` の先へ押し出す結果は、
しきい値超過のエントリと同じく arena へ追記する。アーカイブに書かれるバイトは結果が
どこに保持されたかに依存しないので、出力は決定的なままである。既存の決定性テストが
ゲートで、新たに同じ入力を無制限予算と予算 0 で pack してバイト単位で比較する
テストを加えた。ピークメモリは入力件数と独立に有界になる: 小ファイルフェーズは
処理中バッファ + 保持予算（およそ `2 × cores × 16 MiB`）、大ファイルフェーズは波の
`cores × 2 × blockSize` + 保持予算（およそ `3 × cores × 16 MiB`、最悪ケース）。
ADR-0002 のメモリに関する記述は本記録を指すように修正する。

### テストハーネス

テストスイート内の外部ツール実行は `LC_ALL=C` を固定し、開発者のロケールに
関わらず出力をデコードできるようにする。

## Consequences

**良い点**

- 失敗した展開が、自分が作っていないものを削除することはなくなる。ADR-0001 の
  不変条件「失敗した展開は自分が作ったものだけを片付ける」が、計画ではなく記録
  された事実の上に載り、取られたフォルダ名は何も書く前に展開を失敗させる。
- 重複検査が展開と同じバイトを見るようになり、ADR-0001 §3 の「重複・EOF 超過の
  範囲はオープン時に拒否」の保証が回復する。
- どの段階で失敗しても一時ファイルは失敗した圧縮より長生きできず、pack の実行中に
  存在する一時ファイルは隠しファイル最大 1 つ。
- 圧縮中のメモリは、ADR-0002 がすでに主張していたとおり、入力件数と独立に有界になる。
- 3 つのクラスが構造で閉じ、ソースを読むテストで固定される: 失敗経路が必ず通る台帳、
  範囲の唯一の導出、総量にかかる唯一の予算、一時領域の唯一の寿命。

**悪い点 / 受け入れるトレードオフ**

- 一意性確認と作成の隙間に他プロセスがトップレベル名を取った場合、展開は `File
  exists` で失敗する。以前は展開が進行した（他者のディレクトリの中へ、あるいは失敗
  して他者のファイルを削除）。失敗が安全側の挙動で、窓はフォルダでは最初の書き込み前の
  数ミリ秒、トップレベルのファイルではそのファイルに到達するまで。
- *残余:* 展開の実行中に第三者が所有フォルダの中へ置いたもの（Finder の `.DS_Store`、
  利用者の保存）は、失敗時にそのフォルダと一緒に削除される。台帳が記録するのは
  トップレベル項目で、その下の全パスではない。
- アーカイブのオープンに各ファイルエントリのローカルヘッダの読み取りがかかる —
  窓読みなので、10 万件の小さなエントリで数百回。署名が不正、または長さが EOF を超える
  ローカルヘッダは、以前はそのエントリだけが展開時に失敗していたが、現在は `inspect`
  を含めアーカイブ全体をオープン時に拒否する。「救済せず拒否」と整合する。ディレクトリ
  エントリは従来どおり検査対象外。
- 小さなファイル多数の大きなコーパスでは、以前より多くの結果がアーカイブの隣の arena
  へ退避する。書き込みフェーズはいずれにせよそれを順に吸い出すので、追加コストはメモリ
  上限と引き換えのディスク I/O。arena は pack の間、作成中のアーカイブとほぼ同じ容量を
  出力先ボリューム上に占める。

## Alternatives considered

- **A: 別台帳ではなく予定項目ごとの `created` フラグ。** 情報は同じだが、失敗経路は
  依然として予定一覧を走査し、すべての作成箇所がフラグを立てることに依存する。台帳は
  予定名を後始末から到達不能にし、それがクラスを閉じる性質である。
- **A: 排他作成が `EEXIST` になったら次の番号付き名で再試行。** 推測で競合を修復し、
  リネーム報告を複雑にする。不採用: 救済せず拒否する（ADR-0001）。この事例は 2 つの
  並行する書き手の競合であり、利用者が見るべきもの。
- **A: トップレベル項目を初回使用時に遅延 claim**（初稿）。単純だが、確認から作成までの
  窓を展開の全時間開いたままにする。設計検証で却下。フォルダは前倒しで claim する。
- **A: エントリごとの一時ファイルを残し、1 つの `defer` から解放**（初稿）。列挙分岐の
  事例は閉じるがエントリごとの寿命が残り、予算導入後はユーザーのフォルダに数千の
  ファイル — ファイルサーバでは各々がネットワーク越しの create/write/open/unlink —
  を置くことになる。設計検証で却下、arena を採用。
- **A: 分岐ごとの `abandon()` を残し、欠けている呼び出しを足す。** クラス規則が退ける
  インスタンス修正そのもの — 次に加わる出口でまた漏れる。
- **B: 検査と `extract` の両方でローカルヘッダを読む。** 今日たまたま一致する 2 つの
  導出。クラスは「2 つの導出」なので、修正は 1 つにすること。
- **B: 展開時に遅延して範囲を検証。** オープンは安くなるが、アーカイブは受理され、
  `inspect` は問題なしと報告し、拒否はファイルを書いた後に届き得る。ADR-0001 §3 は
  オープン時の拒否を要求する。
- **C: 他が圧縮中に完了エントリを書き出すストリーミングパイプライン**（予算ではなく
  ウィンドウでメモリを有界化）。長期的には正しい形でレビュワーの提案でもあるが、
  ADR-0002 の 2 フェーズ構造とその決定性の論拠を解消してしまう。保留。予算が実用上
  不足すると判明したら再検討する。
- **C: 固定の予算定数（例: 256 MiB）。** どの定数もどこかの機体で誤る。`cores ×
  spillThreshold` は既存のノブを再利用し、ADR-0002 がすでに文書化している上限である。
- **テストが書き換える `static var` のノブ**（本プロジェクトの従来パターン、
  `blockParallelThreshold`）。テスト間で漏れるプロセス全域の状態で、Swift 6 では
  `nonisolated(unsafe)` が要る。設計検証で却下。`Limits` を呼び出しごとに渡す。
  `blockParallelThreshold` 自体は従来のまま — 対象外。
- **ZP-01 の 2 プロセス競合 E2E。** 本質的に非決定的。進捗コールバックへの介入は
  他者の作成をちょうどその窓に着地させ、同じ `EEXIST` の結果を毎回再現する。
- **ハーネス: ツール出力の損失許容デコード。** 通るが、出力がロケールで変わる。
  ロケール固定は出力をどこでも同じにする。

**そのままは採用しなかったレビュワー提案。** 「ディレクトリの再利用と新規作成を
区別する」は、トップレベル項目を一切再利用しないことで置き換えられる。「圧縮と
順序を守った書き出しを組み合わせる」は上記の保留したパイプラインである。

## Verification

- 事例ごとの振る舞いテスト（`HardeningTests`、`ScratchLifecycleTests`）: レビュワーの
  競合書き手の再現、予定名にあるリンク切れシンボリックリンク、最初の進捗コールバック
  時点でのフォルダ存在、競合相手のトップレベルファイルは残り自分のものは削除される;
  仕様から組んだ 3 本のフィクスチャ（`hostile-overlap-local-extra`、
  `hostile-overlap-local-name`、`hostile-extra-past-eof`）のオープン時拒否; 初回書き込み・
  後続書き込み・クローズ・ブロック並列・バッチ途中の失敗と、pack の成功・キャンセル・
  失敗での arena 削除; 100 KiB 予算内の保持量; 64 並行予約で正確な台帳; 予算 ∞ と
  予算 0 の pack のバイト同一; 強制退避の AES-256 と ZipCrypto 往復。
- `ArchitectureTests` はエンジンのソースを（コメント行を除いて）読む: `Unpacker` に
  `removeItem` も寛容なラッパー作成も無い; `PathUtil` とトップレベル確認に `fileExists`
  が無い; `ZipReader` でローカル名前長・extra 長の読み取りが 1 回、`dataOffset` の代入が
  1 回; `ParallelCompressor` にオープナ 1 つ、削除者 1 つ、新しい static 無し。
- 実バイナリ: レビュワーの ZP-03 手法 — 試し圧縮が「圧縮する」と判定する 40 MiB 入力を
  `RLIMIT_FSIZE` = 20 MiB で `pack` — は「The file couldn't be saved」で失敗し、出力
  フォルダに何も残さない。実際に満杯の 20 MiB RAM ディスク（HFS+）への同じ pack は
  「空き容量不足」で失敗して何も残さず、30 MiB を宣言するアーカイブの unpack は書き込み
  前に拒否される。10 万エントリのアーカイブのオープンと一覧は 0.4 秒。既存の 8 本の
  敵対的フィクスチャはバイト同一に再生成される。
