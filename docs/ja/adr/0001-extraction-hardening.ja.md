# ADR-0001: 展開のハードニング — 解凍爆弾・データ重複・quarantine・重複名

| 項目 | 内容 |
|------|------|
| Status | **Accepted** |
| Date | 2026-08-01 |
| Decision makers | nlink-jp maintainers |
| Triggered by | v0.1.0 後の脅威棚卸し: 展開ツールとは、攻撃者が選んだ構造をユーザーのファイルシステム上で実行するプログラムである |

> もとは `nlink-jp/.github` の組織 ADR-012 として記録していた。
> 2026-08-03 にここへ移設。組織の ADR ログは組織全体を拘束する決定のための
> ものであり、この決定が拘束するのは 1 つのアプリだけである。

## Context

`zip-porter` v0.1.0 の展開処理は、古典的なファイルシステム脱出攻撃をすでに
拒否している。`Unpacker.sanitize` が絶対パス・`..` によるトラバーサル・
Windows のドライブレター・NTFS の代替データストリーム名を弾き、シンボリック
リンクのエントリは作成・展開の双方でスキップし、AES エントリは HMAC 認証・
それ以外は CRC 検証を行い、パーミッションビットは `0o777` でマスクして
setuid/setgid が残らないようにしている。

残りを棚卸しした結果、4 つの欠落が見つかった。3 つはリソースまたは整合性の
問題で、1 つは Gatekeeper のバイパスである。最後のものは macOS ユーザーが
依存している保護を無言で外してしまうため、他より重い。

**1. 解凍爆弾の検出が遅すぎる。** サイズはセントラルディレクトリ由来で、
エントリの処理が**終わってから**検査される。1 KB と宣言して 50 GB に展開される
エントリは、50 GB を書いた後で初めてサイズ検査に落ちる。正しさは保たれるが
可用性は保たれない。

**2. エントリのデータ重複を検出していない。** 正当な ZIP では各エントリの
ローカルヘッダ＋データは互いに重ならないバイト範囲を占める。`42.zip` 系の
爆弾は、セントラルディレクトリの数千件のエントリを**同一の**圧縮データに
向けることで、42 KB のファイルをペタバイトに膨らませる。v0.1.0 には範囲の
一致に気づく仕組みがない。

**3. quarantine を伝播していない。** macOS はダウンロードしたファイルに
`com.apple.quarantine` 拡張属性を付ける。アーカイブユーティリティも
The Unarchiver も、展開したすべての項目にこの属性を複製するため、ZIP の中に
入って届いた実行可能ファイルも Gatekeeper の検査を受ける。zip-porter v0.1.0 は
印の付いていない新しいファイルを書く。アーカイブユーティリティを zip-porter に
置き換えたユーザーは、ZIP の中身に対する Gatekeeper を失うことになる。
置き換え対象より安全でなくなるという退行であり、4 つの中で最も影響が大きい。

**4. 重複するエントリ名が無言で上書きされる。** デコード後の名前が衝突する
2 つのエントリ（大文字小文字のみの差や NFC/NFD の差も含む。APFS は既定で
これらを同一ファイルとして扱う）は、後勝ちで解決される。アーカイブは一覧では
無害なファイルを見せておいて、展開時に静かに差し替えることができる。

ライブラリとは前提が違う。zip-porter は信用できないダウンロード物をユーザーが
ドロップする GUI であり、システムの `.zip` ハンドラとして登録される。

## Decision

**展開処理を 5 つの軸でハードニングする。すべて `ZipPorterCore` 側で強制し、
GUI と CLI が食い違わないようにする。修復ではなく拒否する — 構造的に不正な
アーカイブは救済対象ではなくエラーである。**

### 1. ストリーミング中の fail-fast なサイズ強制

展開しながらエントリごとの書き込みバイト数を追跡し、出力がセントラル
ディレクトリの宣言サイズを超えた瞬間に中断する（`sizeExceedsDeclared`）。
途中まで書いたファイルは既存のエントリ単位クリーンアップ経路が削除する。
「無制限に書いてから文句を言う」を「有界に書いてから文句を言う」に変える
だけで、コストは出力チャンクあたり比較 1 回。

固定の圧縮率上限に置き換えるのではなく、宣言サイズを正典とする。圧縮率だけでは
判別材料として弱く（スパースなデータや高度に反復的なデータの正当なアーカイブは
4 桁に達する）、宣言サイズという契約は厳密であり、そもそもフォーマットの一部で
ある。

### 2. 書き込み前に検査するアーカイブ全体のバジェット

最初の 1 バイトを書く前に、宣言された非圧縮サイズを合計し、展開先ボリュームの
空き容量と比較して、64 MiB のマージンを残して収まることを要求する。足りない
場合は展開を**始める前に** `insufficientSpace` を出す。

各エントリが自分のサイズについて正直であっても、重複型の爆弾がディスクを
食い潰すのを実際に止めるのはこの検査である。同時に「そもそも空きが少なかった」
という日常的なケースも、中途半端な展開ではなく明確なメッセージに変わる。
固定のバイト上限は設けない。ユーザーの空き容量こそが自然なバジェットであり、
どんな定数を選んでも誰かにとっては間違いになる。

### 3. エントリのデータ重複は即座に拒否する

オープン時に各エントリの `[localHeaderOffset, dataEnd)` 範囲を計算し、互いに
重ならずファイル内に収まっていることを検証する。重複があればアーカイブ全体を
`overlappingEntries` で失敗させる。正当なライタは重複を生成しないので、これは
ヒューリスティックではなく構造的妥当性の検査であり、`42.zip` 型の構成を
リソース枯渇によってではなく解析時点で拒否できる。

検査はエントリ数に対して O(n log n)、対象はすでに解析済みのデータ。

> **ADR-0005 による修正（2026-09-05）。** 初出荷時、範囲の終端は中央ディレクトリ
> から近似（`offset + 30 + 名前長 + 圧縮サイズ`）していたが、展開は*ローカル*
> ヘッダの名前長と extra 長から読んでいた — フォーマットが一致を要求しない
> 2 つの導出で、別のローカルヘッダを隠せるだけ大きな extra フィールドは検査を
> 通った。範囲は現在、オープン時に各エントリのローカルヘッダから 1 回だけ解決し、
> `extract` も同じ `dataOffset` を読む。上の「すでに解析済みのデータ」は成り立たなく
> なった: オープンにはファイルエントリ 1 件あたり 30 バイトの読み取りがかかる。

### 4. quarantine の伝播

元アーカイブが `com.apple.quarantine` を持つ場合、そこから生成したすべての
ファイルとディレクトリにその属性を複製する。アーカイブユーティリティおよび
The Unarchiver と同等になり、「アプリがダウンロードされたバイナリを開いた」と
「Gatekeeper がダウンロードされたバイナリを評価した」の差を埋める。

`XattrUtil` の `getxattr`/`setxattr` で実装し、展開が mtime とパーミッションを
設定するのと同じ場所で適用する。元に quarantine 属性が無い場合（ローカルで
作ったアーカイブ）は何も付けない。

### 5. 重複するエントリ名は上書きせず一意化する

正規化キー（NFC + case-fold。APFS の既定挙動に合わせる）でアーカイブ全体の
衝突を検出し、後続のエントリを `name 2` / `name 3` … として展開する。既存の
衝突ポリシーを再利用し、何をリネームしたかを警告に列挙する。ロスレスであり、
ユーザーはすべてのエントリを受け取り、既存ファイルも先に展開したものも
置き換えられない。

そのようなアーカイブを拒否する案は検討して見送った。重複名は連結系のツールに
よって実世界で生じるし、安全側の挙動（両方残す）は何も失わない。

### 付随する変更

セントラルディレクトリのサイズ上限を 2 GiB から 256 MiB に下げる。100 万
エントリでセントラルディレクトリはおよそ 100 MB なので、現実のアーカイブより
十分に上に留めつつ、展開前のアロケーションを有界にできる。

## Consequences

**Positive**

- リソース枯渇の 3 経路（単一エントリ爆弾・重複爆弾・ディスクフル）が、
  ボリュームを埋める前に名前の付いたエラーで早期に失敗する。
- ZIP の中身に対する Gatekeeper が維持され、zip-porter が置き換え対象より
  安全でなくなっていた唯一の欠落が塞がる。
- 検査は両フロントエンドの下層にあるので、GUI も CLI もすべて継承する。
- 重複を構造的に拒否することで、`inspect` が敵対的アーカイブに対して意味の
  ある判定を返せるようになる。

**Negative / accepted trade-offs**

- 事前の空き容量検査は展開先の空きを読むため、実際には収まる展開を拒否し
  うる（圧縮ボリューム上の、ほぼ `store` のアーカイブなど）。許容する:
  64 MiB のマージンと、倍率ではなく宣言サイズを使うことで誤拒否は稀に留まり、
  エラーは不足量を明示する。
- quarantine 伝播により、ダウンロードしたアーカイブから展開したファイルは
  初回起動時に確認が出るようになる。これは macOS の意図した挙動であり他の
  展開ツールとも一致するが、v0.1.0 の出力に印が付かないことに慣れたユーザーに
  とっては目に見える変化である。
- 重複名の一意化は、アーカイブの最後のエントリが勝つと期待していたユーザーを
  驚かせうる。警告が各リネームを明示する。

**Verification**

敵対的なフィクスチャは、自前のライタ（これらの構造を作れない）ではなく仕様から
起こした Python ビルダーで生成する: サイズを偽る爆弾、セントラルディレクトリが
多数のエントリを 1 つのデータ範囲に向ける重複爆弾、大文字小文字のみの衝突を
含む重複名アーカイブ。quarantine 伝播は、実アーカイブを `xattr` で印付けして
展開結果を確認する形で end-to-end で検証する。

**v0.2.0** としてリリース（挙動の追加なので、org のバージョニング規約に従い
0.x のマイナーを上げる）。
