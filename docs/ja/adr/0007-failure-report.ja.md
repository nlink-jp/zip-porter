# ADR-0007: 名前を含まない、コピーできる失敗報告

| 項目 | 値 |
|------|-----|
| 状態 | **採用** |
| 日付 | 2026-11-01 |
| 決定者 | nlink-jp メンテナ |
| 契機 | Deflate64 の失敗（ADR-0006）が、メンテナには「展開エラー」としか届かなかった — 画面にあった唯一の手がかりが伝言を通らなかった |

## 背景

ADR-0006 に至った失敗は、推定で原因を突き止めた。アーカイブは機密で共有でき
ず、エラーに遭った人からは「展開に失敗した」としか伝わらなかった。v0.12.0 まで
のアラートには実は `unsupportedMethod(9)` ——原因そのもの——が出ていた。しかし
アラートの文は選択しにくく、読む人には意味が分からず、口頭で伝えるときに真っ先
に落ちる。問題は ZipPorter の言うことが少ないことより、言ったことが届かないこと
にある。

コードを読むと、ほかに 3 つの穴があった。

1. **CRC 不一致と認証失敗で項目が落ちる。** どちらも「壊れているか改ざんされて
   いる」だけで、どの項目かが分からない。
2. **想定外のエラーが素性を失う。** 代替表示は enum の Swift 表記か
   `localizedDescription` で、`NSError` なら開発側が手がかりにできる domain と
   code が捨てられる。壊れた Deflate ストリームは
   「ZipPorterCore.DeflateStream.Failure error 1」として出る。
3. **バッチは失敗を文字列で持つ。** `ExtractionBatch.Failure` は画面用に組んだ
   文しか持たないので、あとから何も取り出せない。

Windows の ZIP を受け取る人は、まさにそれを共有できない人である。報告に何が入る
にせよ、機密が含まれていないか確かめる手間なしに送れなければならない。

## 決定

**失敗時に「詳細をコピー」操作を用意し、平文の報告をクリップボードに入れる。報告
はアーカイブの構造とエラーを記述し、ファイル名・パス・中身・パスワードは決して
含まない。**

### 利用者に見えるもの

- 画面の文はこれまでどおり平易・ローカライズ済み・技術的詳細なし（組織の状態表示
  の指針どおり）。
- エラーアラート（作成の失敗、何も展開できなかった展開）に 2 つ目のボタン
  **詳細をコピー** を足す。報告をコピーしてアラートを閉じる（NSAlert のボタンの
  標準動作）。既定ボタンは OK のまま。
- 一部のアーカイブが失敗したバッチの結果シートにも、完了の隣に同じボタンを足す。
  失敗があるときだけ出す。こちらは閉じずにコピーする——シートには利用者が読んで
  いる結果がまだ出ているため。
- `zip-porter unpack --report` はエラー行のあとに同じ報告を stderr に出す。
  ターミナルの利用者にも同じ文を頼める。

新しい窓も開閉する欄も作らない。すでに出ているダイアログにボタンを 1 つ足すだけ。

### 報告の中身

英語のみ・固定書式・ASCII のみ。読むのは開発側で、ローカライズすると報告どうしの
比較が難しくなり、送る人のメールソフトを通る。macOS の行は版の数値とビルド番号から
組み立てる——既製の `operatingSystemVersionString` はローカライズされるため。

- ZipPorter の版、macOS の版、操作（作成／展開）。
- 失敗したアーカイブごとに、名前ではなく番号（`archive 2 of 3`）で:
  - エラー: 型とケース、および名前を含みえないペイロードだけ（方式番号・バイト数・
    オフセット・Deflate64 の理由）。ZipPorter が定義していないエラーは `NSError`
    の domain と code、およびその underlying error の同じもの。
    `localizedDescription` は入れない——ファイル名を引用することが多いため。
  - アーカイブの構造: ファイルサイズ、項目数、ZIP64 の EOCD の有無、圧縮方式ごと・
    暗号の種類ごと・作成元（made by）のホストと版ごと・必要版（version needed）
    ごとの項目数、データディスクリプタと UTF-8 名フラグを使う項目数、出現する拡張
    フィールドの ID。
  - 展開が項目に達していれば失敗した項目: 中央ディレクトリ上の位置、方式、フラグ、
    作成元と必要版、圧縮前後のサイズ、拡張フィールドの ID。
- 構造は中央ディレクトリだけから読む。ローカルヘッダや範囲の重なりで開くときに
  拒否されたアーカイブも記述できる。中央ディレクトリ自体が解析できないときだけ
  構造を「読み取れない」と報告する——エラー行に解析が見たものが入っている。
- 拡張フィールドの ID は、各フィールドの長さの合計が拡張領域にぴったり一致する
  ときだけ報告する。1 つの長さが狂うと、それ以降はフィールドの中身を ID として
  読んでしまい、Unicode Path フィールド（0x7075）には項目名が入っている。そう
  いう項目は「malformed」と出す。
- CRC と日時も入れない。CRC は中身の指紋になり、日時はいつ作業したかを語る。
- **作成**の失敗は、環境とエラーのケースだけを報告する。`ZipWriterError` と
  `Packer.Failure` のペイロードはどれも名前・パス・それを引用した文なので、
  どれも出さない。作成する人は手元にファイルを持っていて説明できるので、この
  残余は独自の構造を足さずに受け入れる。

アーカイブ自身のファイル名も入れない。項目名と同じくらい中身を語りうる。

### 下回りの変更

- `ZipReaderError.entryCorrupt(entryName:detail:)` を足し、項目名を埋め込んでいた
  2 つの `.corrupt` 文字列（Deflate64 の失敗、サイズ不一致）を置き換える。これまで
  素の `DeflateStream.Failure` として漏れていた Deflate ストリームの失敗もこれで
  運ぶ。名前がすべてラベル付きの `entryName` に入るので、報告は文字列を掃除する
  のではなく構造として名前を外せる。
- `ZipEntry` に `versionNeeded` と中央ディレクトリの拡張フィールド ID を持たせ、
  `ZipReader` は ZIP64 EOCD の有無を記録する。
- `Unpacker.unpack` に `failingEntry` コールバックを足す。展開が例外を投げたとき、
  展開中だった項目の中央ディレクトリ上の番号を受け取る。投げるエラー自体は変えない
  ので、既存の `catch`（パスワード再試行、CLI のケースごとの文言）はそのまま動く。
- `ExtractionBatch.Failure` は画面の文と並べて報告を持つ。パスワード入力を断った
  場合も報告を持つ——認証失敗はパスワード違いではなく破損のこともあり、報告が
  その見分けになる。
- 失敗した項目には段階（作成・展開・書き込み・クローズ）を付けない。エラー行が
  すでに分けている——読み取り部が見つけたものは `ZipReaderError`、ファイル
  システムが拒んだものは POSIX や Cocoa の domain と code。ディレクトリ項目は
  そうと示す。
- 報告は純関数で組む——構造の要約は ZipPorterCore、報告文はアプリ側の
  `ErrorMessages` の隣——テストを付ける。アーカイブ自身の名前と全項目名に目印を
  入れたアーカイブの報告に、目印が 1 つも入らないことを確かめるテストを含む。
  エラーは明示の switch で描画し、`String(describing:)` は使わない——関連値、
  つまり名前を出力するため。
- 自由文の詳細（`corrupt`、`entryCorrupt` の detail、Inflate64 の理由）は、名前・
  パス・URL を埋め込んだ詳細があれば落ちるソース走査テストで名前なしを保つ。
  詳細を閉じた enum にすればコンパイル時の事実になるが、投げる箇所が数か所なので
  テストが釣り合った守りである。
- 画面では CRC 不一致と破損した項目も項目名を出す（サイズの文言はすでに出して
  いた）。（認証失敗はこれまでどおりパスワード入力に回る。）CLI の 1 行の
  メッセージはファイル名を出すことがあるが、`--report` の報告は決して出さない。

## 検討した代替案

- **項目名を含める。** 切り分けは楽になる（名前から作成ツールが分かることがある）
  が、送る前に中身を確かめなければならないものになる。この機能が対象とするのは
  中身を共有できない人である。メンテナが却下（2026-11-01）。
- **アラート自体に詳細を出す**（開閉する欄や長い本文）。画面に多く出しても、すでに
  出ていた `unsupportedMethod(9)` 以上には届かず、実装の詳細を全員の目の前に置く。
- **ログファイルに書く。** 頼まれてログファイルを見つけられる人はいない。
  クリップボードなら頼んだ相手への返信に 1 回貼るだけ。
- **CLI では常に報告を出す。** スクリプトが失敗のたびに複数行を受け取る。明示の
  フラグにすれば stderr は 1 行のまま。
- **`pack --report`。** 作成の報告はエラーのケースしか持たず、それは 1 行の
  メッセージがすでに言っている。

## 結果

- 報告は、ファイルなしで「どの作成ツール・どの方式・どんな形の項目か」に答える
  ——ADR-0006 で推定に頼った問い。
- 一部の切り分け情報は意図して手放す: 名前、コメント、`localizedDescription`。
  画面の文がどのファイルを書けなかったかを言っていても、報告には
  `NSCocoaErrorDomain 640` としか出ないことがある。画面の文は利用者には見えている。
- 新しいエラーケースは名前をラベル付きの `entryName` に入れること。報告の描画は
  ZipPorter 自身のエラーに対して網羅的な switch なので、新しいケースは何を報告
  するか決めるまでコンパイルが通らない。
