# ADR-0004: リクエスト単位の完了報告と trigger スケジュール通知

| 項目 | 内容 |
|------|------|
| Status | **Accepted** |
| Date | 2026-08-03 |
| Decision makers | nlink-jp maintainers |
| Triggered by | 実使用: Finder で複数の ZIP を選択してワンショット起動すると、アーカイブごとに別々に報告され、最後のバナーしか読めない |

> もとは `nlink-jp/.github` の組織 ADR-016 として記録していた。
> 2026-08-03 にここへ移設。組織の ADR ログは組織全体を拘束する決定のための
> ものであり、この決定が拘束するのは 1 つのアプリだけである。

## Context

問題は 2 つ、根は 1 つ。

**アーカイブ単位の報告。** Finder は複数選択を **1 回**の
`application(_:open:)` に全 URL をまとめて配送する（実測: 3 件が 1 イベントで
到着）。にもかかわらずアプリは各アーカイブを個別のジョブとして扱い、個別に
報告していた。3 件での実測:

```
open(3): m-1.zip,m-2.zip,m-3.zip
announce: … m-1  (+0.10 s)
announce: … m-2  (+1.12 s)
announce: … m-3  (+2.37 s)
```

macOS は同一アプリのバナーを次のバナーで置き換えるため、t=4.0 s に画面上に
残っていたのは 3 枚目だけだった。ユーザーは 3 個展開して 1 個分しか読めない。
アーカイブ単位の繰り返しはそれだけに留まらない。通知センターに N 件が残り、
`activateFileViewerSelecting` が N 回発火して Finder が飛び回り、完了表示が
*ダイアログ*設定なら OK を N 回、展開先が*毎回確認*ならパネルが N 回、ほぼ確実に
同じパスワードを共有しているアーカイブ群に対してプロンプトが N 回出る。進捗
シートは N 回ゼロから作り直され「3 件中 2 件目」という感覚が得られず、エラーも
アーカイブごとに別々のアラートになる。

**遅延終了。** v0.8.2 以降、Finder から起動した処理は完了バナーを投げたあと
`.accessory` に降格して約 4.5 秒プロセスを生かしていた。フォアグラウンド提示
された通知はアプリの終了とともに取り下げられるからである。この窓 — 見た目は
消えているのに実際は生きていて、open イベントを受け取り続ける — が、v0.10.3 の
データ損失（展開が書き込み中に打ち切られ、切り詰められたファイルがエラーなしで
残った）の正体だった。v0.10.3 で終了をキャンセル可能にし発火時に再判定するよう
にしたが、窓そのものは残っていた。またバッチ内では各アーカイブが自分のバナー
儀式を待つため、アーカイブ**間**に約 1.2 秒の空転を生んでいた。

署名済み実バイナリで実測（固定時刻のスクリーンショット）:

| 方式 | プロセス生存 | バナー |
|------|--------------|--------|
| v0.10.3 の出荷状態 | 0.2 → **6.3 s** | t=3.0 s 表示、t=7.0 s には消滅 |
| `trigger: nil`、提示時点で terminate | 0.16 → 1.17 s | **t=1.5 s で不在** |
| **`UNTimeIntervalNotificationTrigger(0.5)`、`add` 後に terminate** | 0.16 → **0.57 s** | t=1.5 s **および** 5.0 s で表示 |
| 同、0.1 s | 0.12 → **0.47 s** | t=2.0 s で表示 |

2 行目は v0.8.2 の観測が正しかったことを裏付ける。3・4 行目はその適用範囲を
示す。これは通知の性質ではなく、`willPresent` を経由する**即時配送**の性質で
ある。trigger でスケジュールすれば提示は `notificationd` のものになり、投稿した
プロセスがとうに死んでいてもバナーは出て、寿命を全うする。

## Decision

**完了通知を time-interval trigger でスケジュールし、アーカイブごとではなく
リクエスト全体で 1 回報告する。**

1. **trigger スケジュール通知。**
   `UNTimeIntervalNotificationTrigger(timeInterval: 0.1, repeats: false)` で
   投稿し、`add` が成功した時点で呼び出し側の completion を走らせる。0.1 秒の
   遅延は知覚できず、アプリは自分のバナーを見届ける必要がなくなる。
2. **遅延終了を廃止。** `bannerLifetime`、`remainingBannerTime`、`.accessory`
   への降格、キャンセル可能な `DispatchWorkItem`、`OneShotQuit.afterBanner` を
   すべて削除する。`OneShotQuit` は `.now` / `.stay` に縮退する。実際に処理を
   守っている規則は残し、かつ最優先とする。busy — 実行中・キュー待ち・ユーザー
   待ち — は常に勝ち、処理中に届いた要求は捨てずにキューに積み、ユーザーが
   アプリを自分のものにした（ドロップ・Dock クリック・設定）ならワンショット
   セッションは終了する。
3. **1 リクエスト = 1 バッチ。** 1 回の `handle(urls)` — Finder の複数選択 1 回、
   ドロップ 1 回 — が、進捗シート 1 枚、完了報告 1 回、Finder 表示 1 回を生む。
   - 進捗: 全アーカイブの合計を分母とする確定バーを 1 本、状況行は
     「3 件中 2 件目 — foo.zip」。
   - 完了: 「3 個のアーカイブを展開しました — 24 ファイル・3 フォルダ」。
     報告事項（スキップしたシンボリックリンク、安全でないパス、重複名の
     リネーム、quarantine 付与の失敗）はバッチ全体で統合し、ADR-0001 のとおり
     報告事項があれば完了表示の設定に関わらずダイアログを強制する。
   - 失敗はバッチを中断しない。残りのアーカイブは処理し、結果は
     「3 個中 2 個のアーカイブを展開しました — 1 個失敗」として失敗を列挙する。
     一部失敗したバッチは必ずダイアログにする。バナーは失敗を伝える場所では
     ない。
   - Finder 表示は最後に 1 回、バッチの最上位項目に対して行う。
4. **確認はバッチにつき 1 回。** 展開先パネル（展開先=*毎回確認*）は 1 回だけ
   表示してバッチ全体に適用する。あるアーカイブで入力したパスワードは次の
   アーカイブでまず試し、失敗したときだけ改めて尋ねる。

単一アーカイブの挙動は同じコード経路の N=1 のケースであり、文言は現状のまま
とする。

## Consequences

**Positive**

- 複数選択が、N 枚のうち 1 枚しか生き残らないバナーではなく、読める結果 1 つを
  生む。通知センターのエントリも N 件から 1 件になる。
- 「Dock から消えているのに生きている」窓が消滅するので、v0.10.3 の背後にあった
  バグのクラスは防御対象ではなく**到達不能**になる。ワンショットのプロセス寿命は
  約 6.3 秒から約 0.4 秒になり、バッチ内の約 1.2 秒/件の空転も消える。
- バッチあたりの中断が減る: 展開先パネル 1 回、共有パスワード 1 回、Finder の
  ジャンプ 1 回。

**Negative / accepted trade-offs**

- アプリ終了後にバナーをクリックすると ZipPorter が再起動する。ドロップレット
  ウィンドウを出す代わりに、通知への応答で結果を Finder に表示することで扱う。
- バッチ報告は粒度が粗い。30 個のアーカイブなら合計値と先頭数件の報告事項を
  示すのであって、全アーカイブを列挙するわけではない。報告すべきことがある
  場合はダイアログが完全な一覧を運ぶ。
- 表示を 1 回にまとめるため、展開先が異なるフォルダに散らばるバッチでは
  Finder が複数選択に対して選ぶ挙動に従うことになる。N 回連続でジャンプする
  よりはよいと判断した。
- パスワードを次のアーカイブへ持ち回すため、バッチの間はメモリ上に保持される
  （1 アーカイブのリトライループ内ではすでにそうなっていた）。どこにも書かず、
  バッチ終了時に破棄する。
